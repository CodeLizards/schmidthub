## Observed submission choices

- **Entry type:** Patents; Technology & Equipment; Scientific Datasets; Academic Research; Creative Works.
- **Subject matter:** Clean Energy; Climate & Environment; Data & Computing; Health & Medicine; Ocean Sciences.
- **Target goals (multiple selection):** Content Discussion Only; Private Commercial Licensing; Open Licensing; Full Assignment of Intellectual Property.
- **Preferred license:** Open Research License; Apache 2.0; MIT; CC BY 4.0; Commercial License; Full IP Assignment; Custom License Agreement.

The existing-entry editor includes Tags; the new-entry wizard inspected here does not. Preserve that distinction unless the wireframe is updated.

## Questions the wireframes do not settle

| ID | Evidence / conflict | Required resolution |
| --- | --- | --- |
| Q1 | WF13 technical approval requests legal review; WF17 Program Admin has Approve & publish | Confirm administrator override authority and how it coexists with legal review. Preserve both visible actions; do not silently remove either. |
| Q2 | WF09 published records offer Save changes; WF18 admin edits explicitly apply immediately | Confirm submitter edit effects. Admin edits must retain the visible immediate behavior, with technical history/audit protection. Do not assume a new approval cycle for every edit. |
| Q3 | WF10/WF22 visibility checkbox describes public indexing | Confirm whether direct access is also restricted and to whom. The user-required outer pilot gate applies regardless. |
| Q4 | WF12 describes eligibility but no controls for domain trust management | Define verification and failure behavior as backend policy; no new trust-administration screen is authorized. |
| Q5 | WF20 licensing/return/turnaround rates have labels but no formulas | Define measures behind those exact labels; no new analytics features. |
| Q6 | WF21 ZIP association, row schema and error correction detail are incomplete | Specify processing/validation contracts; add no mapping screen without a wireframe update. |
| Q7 | WF22 Create Draft has no account; link expiry and successful submission tracking shown | Define how a guest resumes a draft and when the link is consumed. Use the visible signed agreement; do not add a second approval screen or e-signature vendor without a requirement. |
| Q8 | WF07 recovery; settings Edit; reviewer decision forms; WF05 confirmation; nested admin dialogs | Inspect the remaining control states and record actual fields before building them. If absent, request clarification instead of inventing UI. |
| Q9 | WF02 placeholders, WF23 counts, WF04 repeated details; WF25 nonfunctional destinations | Use real approved data for functional content. Preserve designed layout; agree placeholder/destination treatment separately. No invented data volumes or new content pages. |
| Q10 | Navigation offers overlapping role experiences; prototype role selector and illustrative data do not define full policy | Confirm role/authority grants, reviewer assignment and self-review rules. These are implementation policy decisions, not new user-facing controls. |

## Evidence boundaries

This is a fresh screen/control audit, not a claim that every final confirmation or nested modal has been exercised. Unresolved states above remain named dependencies in week 1. The plan must not use an unverified state as evidence for a feature or a scope cut.

Database transactions, immutable internal history, authorization, safe uploads, job retries, backups and tests are engineering work needed to make observed actions reliable. Hosting restrictions, real seed data, 5–6 users and one developer with Codex are user requirements. Neither category should be described as a feature found in a wireframe.
